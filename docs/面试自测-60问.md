## 一、项目概览（Q1 ~ Q8）

### Q1：用一句话介绍你的项目。

**答：** AllahPan 是一个面向家庭场景的私有云盘系统。核心能力是文件上传、管理、预览、全文搜索，特色在于异步流水线处理（缩略图生成 + AI OCR 文字提取 + Elasticsearch 索引），以及 MinIO 对象存储、MD5 秒传、分片断点续传等工程实践。

---

### Q2：项目整体架构是怎么设计的？

**答：** 前后端分离 + Maven 多模块单体 + 独立搜索微服务的混合架构。

- **前端**：Vue 3 SPA（Vite 构建，Element Plus UI，Pinia 状态管理，Axios HTTP）
- **后端**：5 个 Maven 模块按严格依赖链组织：`common → security → mbg → core(:8088)`，搜索服务 `search(:8081)` 仅依赖 `common` 独立运行
- **通信**：前端 ↔ core 走 REST + JWT；core ↔ search 走 HTTP（RestTemplate）；core 内部异步处理走 RabbitMQ
- **基础设施**：MySQL 8.0、Redis 7.0、RabbitMQ 3.12、Elasticsearch 8.11 + IK 分词器、MinIO 对象存储，全部 Docker Compose 编排

---

### Q3：为什么把搜索服务单独拆出来？

**答：** 三个原因：

1. **物理隔离**：Elasticsearch 操作（索引重建、搜索查询）比较重，独立部署避免拖慢主应用
2. **独立扩展**：搜索流量大的时候可以单独扩容搜索服务，不影响核心业务
3. **依赖简化**：核心业务不需要引入 ES 依赖，搜索模块也只需要 `common` 模块，两边完全解耦

搜索服务绑定 `127.0.0.1:8081`，只能被 core 本机调用，不直接对外暴露。

## 二、认证与安全（Q9 ~ Q15）

### Q9：项目中用户的认证方式是什么？为什么不用 Session？

**答：** 采用的是**无状态 JWT 认证**。

为什么不选 Session：
- 云盘系统天然需要多端访问（Web、移动端），Session 强绑定服务器内存
- 分布式扩展时 Session 同步很麻烦（需要 Redis 存 Session 或 Sticky Session）
- JWT 自包含用户信息，服务端不需要查 Session 存储，天然支持水平扩展

实现方式：Hutool JWT 生成 HS512 签名 Token，有效期 7 天，Claims 包含 `userId`、`email`、`hasPassword`。

---

### Q10：JWT Token 在整个请求链路中是怎么工作的？

**答：**

1. **登录时**：`AuthController` 调用 `JwtTokenUtil.generateToken(userId, email, hasPassword)` 生成 JWT，返回给前端
2. **每次请求**：前端在 `Authorization: Bearer <token>` 头携带 JWT
3. **过滤器拦截**：`JwtAuthenticationTokenFilter`（`OncePerRequestFilter`）从 Header 提取 token：
   - 去掉 "Bearer " 前缀
   - 从 token 中解析 `subject`（email）
   - 检查 SecurityContext 是否已认证。未认证则：
     - 通过 `UserDetailsService.loadUserByUsername(email)` 加载用户详情（先查 Redis 缓存，未命中查 MySQL）
     - 验证 token 有效性
     - 构建 `UsernamePasswordAuthenticationToken` 注入 `SecurityContext`
4. **白名单路径**：`/api/auth/**`、`/api/share/access/**`、`/api/file/watch`（SSE token 走 query 串）等直接放行

---

### Q11：验证码登录做了哪些安全防护？

**答：** Redis 三层限流防护：

| 层级 | Redis Key | TTL | 规则 |
|------|-----------|-----|------|
| **第1层：发送间隔** | `allahpan:sendLimit:{email}` | 30s | 30 秒内同一个邮箱只能发一次 |
| **第2层：验证码有效期** | `allahpan:authCode:{email}` | 5min | 验证码 5 分钟自动过期 |
| **第3层：小时上限** | `allahpan:attempts:{email}` | 1h | 同一邮箱每小时最多 50 次 |

另外，验证码校验通过后立即删除 Redis key，防止验证码被重复使用。

---

### Q12：Spring Security 是怎么配置无状态认证的？

**答：** 五个关键配置：

1. **`SessionCreationPolicy.STATELESS`** — 不创建 HTTP Session
2. **禁用 CSRF** — 无 Cookie，无 CSRF 风险
3. **白名单 URL `permitAll()`** — 登录接口、分享访问、SSE 端点等不需要认证
4. **自定义 `JwtAuthenticationTokenFilter`** — 加在 `UsernamePasswordAuthenticationFilter` 之前，从 Header 提取 JWT 注入上下文
5. **自定义 401/403 处理器** — `RestAuthenticationEntryPoint` 和 `RestfulAccessDeniedHandler` 返回 JSON（`CommonResult.unauthorized()` / `forbidden()`），而不是 Spring 默认的重定向到登录页

---

### Q13：密码是怎么存储的？为什么首次登录可以不设密码？

**答：** 密码使用 **BCrypt** 哈希存储（`BCryptPasswordEncoder`）。

首次登录用户通过邮箱验证码登录，系统自动注册：
- `password` 字段为 NULL
- `first_login` 标记为 1
- JWT Claims 中 `hasPassword=false` 告诉前端引导用户设置密码

用户设置密码后，`first_login` 变为 0，`hasPassword` 变为 true。后续可以通过密码登录。

设计意图：降低注册门槛，邮箱即身份。

---

### Q14：如果 JWT Token 泄露了怎么处理？

**答：** 当前实现中，JWT 是无状态的，签发后服务端没有主动失效的能力（没有维护 Token 黑名单）。应对策略：

1. **有限有效期**：7 天过期，即使泄露影响窗口有限
2. **后续可优化方向**：
   - 引入 Refresh Token 机制，Access Token 缩短到 15 分钟
   - Redis 维护 Token 黑名单（`JWT_SECRET` 每次更换
   - 记录登录 IP/设备指纹，异常时拒绝

这是一个已知的 trade-off：选择了无状态 JWT 的简单性，牺牲了主动失效能力。对于家庭场景的小规模应用，这是可接受的。

---

### Q15：`RedisCacheAspect` 是干什么的？为什么 AuthCodeService 不走这个切面？

**答：** `RedisCacheAspect` 是一个 AOP 切面，拦截所有 `*CacheService.*` 方法：

- **默认行为**：Redis 异常时 catch 住，打日志，返回 null，调用方无感知
- **`@CacheException` 注解**：标记在方法或类上后，Redis 异常会重新抛出，让调用方感知

设计哲学：缓存是加速层，挂了不应该影响业务。这叫 **best-effort 缓存**。

`AuthCodeServiceImpl` 不走切面是因为它的类名不匹配 `*CacheService`，它直接调 `RedisService`。这是刻意的——验证码是核心业务，Redis 挂了必须报错，不能静默吞异常。

## 三、文件系统（Q16 ~ Q25）

### Q16：文件上传的完整流程是怎样的？

**答：**

```
① 前端 POST /api/file/upload (multipart/form-data)
② FileServiceImpl.upload():
   ├── 校验父文件夹存在
   ├── 构建虚拟路径（从根到父目录拼接）
   ├── DigestInputStream 包装输入流，边写 MinIO 边算 MD5
   ├── MD5 去重检测：
   │   ├── 命中 → 秒传：删除刚上传的 MinIO 对象，复用已有 storageKey，processStatus=3
   │   └── 未命中 → 写入 DB（processStatus=0）+ 发送 RabbitMQ 消息触发流水线
   └── 返回 File 实体 + SSE 广播 file-created
```

关键设计：**上传即返回**，不阻塞等待后续处理。

---

### Q17：MD5 秒传是怎么实现的？为什么用 `DigestInputStream`？

**答：**

秒传逻辑：
1. 文件上传到 MinIO 的同时，用 `DigestInputStream` 包装输入流，逐字节计算 MD5
2. 上传完成后，用 MD5 值查询 `files` 表（`idx_md5_delete` 复合索引）
3. 如果找到相同 MD5 的未删除文件 → 删除刚刚上传的 MinIO 对象（`removeObject`），创建新的 DB 记录，直接指向已有文件的 `storageKey`，`processStatus` 直接设为 3
4. 新记录只关联到当前用户的目录结构，不复制实际文件内容

为什么用 `DigestInputStream`：
- 它是 Java 标准库的装饰器流，包裹原始 InputStream
- `read()` 时数据同时流入两个方向：目标（MinIO）和 MD5 计算器
- **不占额外内存**，不把整个文件加载到堆中，O(1) 空间复杂度
- 对比：先读文件到 `byte[]` 再算 MD5，大文件会 OOM

### Q18：文件的 storageKey 是怎么设计的？为什么这样设计？

**答：**

```
{userId}/{yyyy/MM}/{UUID}{ext}

示例: 1/2026/06/d27fed91-2fed-4e3e-bbcd-ce19dc3410c5.png
```

设计意图：
- **`userId` 前缀**：用户隔离，每个用户的文件在 MinIO 中物理分开
- **`yyyy/MM` 时间分片**：避免单目录文件过多导致对象存储性能下降
- **`UUID + ext`**：保证全局唯一，防止命名冲突
- 保留原始扩展名便于通过后缀识别文件类型

---

### Q19：文件的树形目录结构是怎么实现的？

**答：** 单表 `parent_id` 自引用，非常简单：

```sql
files 表:
  id          BIGINT PK
  parent_id   BIGINT       -- 0=根目录，其他=父文件夹 ID
  is_folder   TINYINT      -- 1=文件夹，0=文件
```

操作层面：
- **列表查询**：`SELECT WHERE parent_id = ? AND delete_time IS NULL ORDER BY is_folder DESC, create_time DESC`（文件夹优先）
- **面包屑导航**：从文件开始往上循环查 `parent_id`，直到根，得到完整路径链
- **递归操作**：删除/恢复文件夹时，递归遍历所有子孙节点

---

### Q20：软删除是怎么设计的？回收站有什么策略？

**答：** 软删除通过 `delete_time` 字段实现：

- `delete_time IS NULL` → 正常文件
- `delete_time IS NOT NULL` → 在垃圾站
- 查询时所有 SQL 都加 `delete_time IS NULL` 条件

文件夹删除会递归设置所有子孙的 `delete_time`。

**回收站策略**：
- 原文件 `copyToTrash` 到 MinIO `allahpan-trash` bucket，再从 `allahpan-files` 删除
- 支持恢复（`restoreFromTrash`）和永久删除（`removeFromTrash`）
- `TrashCleanupTask` 每天凌晨 3 点自动清理超过 60 天的垃圾站文件
- `MinioOrphanCleanupTask` 每天凌晨 4 点双向扫描 MinIO↔DB，清理孤儿对象

---

### Q21：重命名和移动文件夹时需要注意什么？

**答：** 核心难点：文件夹重命名或移动后，所有子孙节点的 `filePath` 都会变化。

处理流程：
1. 更新当前节点：修改 `fileName` 和 `filePath`
2. **递归重建子孙路径**：`rebuildDescendantPaths(fileId)` 遍历所有子孙，重新计算 `filePath`

移动时还有三个额外校验：
- **不能移动到自身**（`targetParentId == fileId`）
- **不能移动到自己的子文件夹**（通过 `isDescendant()` 向上溯源父链检测循环）
- **不能移动到同一父目录**（无操作返回）

---

### Q22：大文件分片上传是怎么实现的？断点续传怎么做的？

**答：** 四个步骤：

```
POST /api/file/chunk/init       → 生成 uploadId (UUID)，在 Redis 创建 Hash 会话 + Set 分片记录
POST /api/file/chunk/upload     → 逐片写入本地临时目录，SADD 记录已传分片
POST /api/file/chunk/complete   → 合并所有分片 → MinIO putObject → MD5 秒传检测 → DB 插入 → 清理临时文件
GET  /api/file/chunk/status/{id} → 查询已传分片列表
```

**断点续传**：调用 `init` 或 `status` 接口时，如果 `uploadId` 已存在（Redis 会话未过期），返回已上传的分片索引列表。前端用 `spark-md5` Web Worker 计算分片 MD5，跳过已上传的分片，只补传缺失的。

**Redis 会话**：Hash 存元数据（fileName, totalChunks, parentId），Set 存已上传分片索引，TTL 24h。每小时定时清理过期会话。

---

### Q23：文件从 MinIO 下载/预览/缩略图是怎么区分的？

**答：** 三个端点，都通过 `MinioUtil` 流式返回，区别在于 HTTP 响应头：

| 端点 | Content-Disposition | 来源 Bucket | 用途 |
|------|---------------------|-------------|------|
| `/api/file/{id}/download` | `attachment` | `allahpan-files` | 触发浏览器下载 |
| `/api/file/{id}/stream` | `inline` | `allahpan-files` | 浏览器内预览（图片/PDF） |
| `/api/file/{id}/thumbnail` | `image/jpeg` | `allahpan-thumbnails` | 缩略图 |

全部通过 `InputStream` 流式传输，不缓冲整个文件到内存。

### Q24：`processStatus` 的状态机是怎么设计的？

**答：**

```
0 (PENDING/等待处理)
  → 1 (THUMBNAIL_GENERATED/缩略图完成)
  → 2 (TEXT_EXTRACTED/文本提取完成)
  → 3 (COMPLETED/全部完成含 ES 索引)

-1 (FAILED/致命错误)
```

特殊情况：
- **秒传文件**：processStatus 直接 = 3
- **文件夹**：processStatus 直接 = 3
- **VIDEO/OTHER 类型**：跳过文本提取阶段，但不影响索引
- **ES 索引失败**：不标记 -1，文件仍可用（降级策略）
- 只有数据库层面致命错误才标记 -1

### Q25：SSE（Server-Sent Events）是怎么实现实时推送的？

**答：**

`SseBroadcaster` 是核心组件（单例 Bean），维护一个 `CopyOnWriteArrayList<SseEmitter>`：

- **订阅**：`GET /api/file/watch?token=xxx` 创建 `SseEmitter`（无限超时），加入列表。token 走 query 串是因为浏览器的 `EventSource` API 不支持自定义 Header
- **广播**：流水线每完成一个阶段 → `broadcast("file-updated", {...})` → 遍历所有 emitter 发送命名事件
- **清理**：`onCompletion` / `onTimeout` / `onError` 回调自动从列表移除

事件类型：
| 事件 | 触发时机 | 数据 |
|------|---------|------|
| `connected` | SSE 连接建立 | 确认消息 |
| `file-created` | 上传完成 | fileId, parentId, fileName |
| `file-updated` | 流水线阶段完成 | fileId, processStatus, thumbnailKey |
| `file-deleted` | 删除操作 | fileId, parentId |

前端 `FileBrowser.vue` 收到事件后自动刷新对应目录的文件列表。

提取 `SseBroadcaster` 为独立组件的原因是：流水线消费者（`FileProcessReceiver`）在 Spring AMQP 监听器线程中运行，不能直接依赖 REST 控制器。提取为独立 Bean 后，控制器和消费者都可以注入它。

## 四、缓存体系（Q26 ~ Q30）

### Q26：项目中 Redis 都存了哪些数据？

**答：**

| Key 模式 | 用途 | TTL |
|----------|------|-----|
| `allahpan:member:{email}` | 用户对象缓存 | 24h ± 随机 0~300s |
| `allahpan:authCode:{email}` | 邮箱验证码 | 5min |
| `allahpan:sendLimit:{email}` | 验证码发送间隔 | 30s |
| `allahpan:attempts:{email}` | 小时发送上限计数 | 1h |
| `allahpan:bloom:user:email` | 布隆过滤器 bitmap | 永久（~12KB） |
| `allahpan:share:{code}` | 分享链接（Redis-only） | expireHours+1h, max 168h |
| `chunk:upload:{uploadId}` | 分片上传会话（Hash + Set） | 24h |

### Q27：布隆过滤器是用来干什么的？怎么实现的？

**答：**

用于**用户邮箱存在性预检**，解决缓存穿透问题。

如果有人用大量不存在的邮箱反复请求，没有布隆过滤器的话，会逐个穿透缓存→查 MySQL，造成数据库压力。

实现：
- 基于 Redis Bitmap，预期 10000 个元素，误判率 1%，7 个哈希函数（SHA-256 派生）
- 占用空间仅 ~12KB
- `BloomFilterInitializer`（`ApplicationRunner`）在应用启动时重建：清空 → 分页查询所有用户邮箱 → 逐条 add
- `UserCacheServiceImpl.getUser()` 先调 `bloomFilterService.mightContain(email)`：
  - 返回 false → 该邮箱**绝对不存在**，直接返回 null，跳过 Redis + MySQL
  - 返回 true → 可能存在（1% 误判），继续正常 Redis → MySQL 流程

即使 1% 误判也只是多一次 MySQL 查询，远好于大量穿透。

---

### Q28：用户缓存的 TTL 设计有什么讲究？

**答：** 用了**随机 TTL 防缓存雪崩**。

```java
实际TTL = 86400s (24h) + ThreadLocalRandom.nextInt(0, 300)
```

原理：如果大量用户缓存在同一时刻过期（比如都在某个整点写入），Redis 瞬间收到大量 DB 查询请求，压力陡增。加上 0-300 秒的随机抖动后，过期时间被摊平到 5 分钟窗口内，避免瞬时高压。

这是一个非常经典且低成本（零额外组件）的防雪崩方案。

---

### Q29：`RedisCacheAspect` 的设计哲学是什么？

**答：** **Best-effort 缓存**——缓存挂了不应该是灾难。

- 拦截所有 `*CacheService.*` 方法
- 默认：Redis 异常 → catch → log.error → return null，调用方无感知
- 需要强依赖 Redis 时：加 `@CacheException` 注解，异常传播给调用方

这体现了"缓存是可选的加速层"的设计理念。验证码服务（`AuthCodeServiceImpl`）不走切面，因为验证码是核心业务，Redis 挂了应该立即报错。

---

### Q30：如果要做一个布隆过滤器不能删除的限制，有什么方案？

**答：** 布隆过滤器的核心局限是**不支持删除**——因为多个元素可能共享同一个 bit，删除一个元素可能影响其他元素的判断。

三种解决方案：

1. **计数布隆过滤器（Counting Bloom Filter）**：每个 bit 替换为计数器，add 时 +1，remove 时 -1。代价是位图变大 4-8 倍
2. **布谷鸟过滤器（Cuckoo Filter）**：原生支持删除，空间效率更高，但删除也有误判可能
3. **定期重建**：本项目采用的方式——启动时清空重建，因为用户数量少（家庭场景），重建成本低

## 五、消息队列与异步处理（Q31 ~ Q38）

### Q31：RabbitMQ 在项目中扮演什么角色？为什么需要它？

**答：** RabbitMQ 是**文件异步处理流水线的编排引擎**。

文件上传后的三个步骤——生成缩略图、AI OCR 提取文字、写入 Elasticsearch——都可能是耗时操作（OCR 可能好几秒），如果同步执行，用户上传一个文件要等很久才能看到响应。

用 RabbitMQ 解耦后：
- **上传接口**：MinIO 存储 + DB 写入 → 立即返回（< 500ms）
- **后台消费**：缩略图 → 文本提取 → ES 索引，逐步完成
- **进度推送**：每阶段完成后通过 SSE 推送给前端

---

### Q32：消息处理的完整流程是怎样的？

**答：**

```
① 上传完成后，FileController 调用 FileProcessSender.sendProcess(UPLOADED)
② 消息发送到 allahpan.file.process 交换机 → 主队列
③ FileProcessReceiver (@RabbitListener) 消费消息
④ 根据 currentStage 分发：
   UPLOADED      → ThumbnailGenerator.generate() → 更新 processStatus=1 → 发 THUMBNAILED 消息
   THUMBNAILED   → TextExtractor.extract()       → 更新 processStatus=2 → 发 TEXT_EXTRACTED 消息
   TEXT_EXTRACTED → EsIndexService.index()       → 更新 processStatus=3 → 完成
⑤ 每个阶段完成后 SSE 广播 file-updated
```

消息体 `FileProcessMessage` 包含：`fileId`、`currentStage`（Stage 枚举）、`retryCount`（0~3）、`lastError`。

---

### Q33：重试机制是怎么设计的？TTL + DLX 回环是什么意思？

**答：** 这是 RabbitMQ 实现延迟重试的经典模式。

**传统方案的问题**：如果在消费者中 `Thread.sleep(30s)` 再重试，会阻塞消费线程，影响其他消息处理。

**TTL + DLX 方案**：

```
消费者处理失败
  → retryCount < 3？
  → FileProcessSender.sendRetry(message, delayMs)
  → 发送到重试交换机 → 重试队列（TTL = delayMs，无消费者）
  → TTL 过期 → DLX 自动转发 → 主交换机 → 主队列 → 消费者重新处理
```

指数退避：30s → 60s → 120s。最多重试 3 次。

这种方法的好处：**不阻塞消费者线程**，消息在 TTL 队列里"躺着"等，过期后再回到主队列被消费。

---

### Q34：重试 3 次后还是失败怎么办？什么叫"优雅降级"？

**答：** 重试耗尽后，根据异常类型分级处理：

| 异常类型 | 判断条件 | 重试耗尽后行为 |
|----------|---------|---------------|
| **基础设施异常** | `ConnectException`、`SocketTimeoutException`、`IOException`、`MinioException`、Ollama 超时 | **优雅降级**：不标记 `-1`，文件保持当前 processStatus。文件仍可正常使用，只是缺少缩略图/文本/索引 |
| **致命异常** | `DataAccessException`（数据库操作失败） | 标记 `processStatus = -1` |

设计理念：**Ollama 挂了不代表你上传的图片就废了。** 宁可缺少 OCR 文字，也不能让用户觉得文件上传失败了。这是面向可用性的设计。

---

### Q35：消息可靠性怎么保证？消息丢了怎么办？

**答：** 当前项目在以下几个层面保证消息可靠性：

1. **持久化**：Exchange 和 Queue 都声明为 `durable=true`，消息持久化到磁盘，RabbitMQ 重启不丢
2. **消息确认**：Spring AMQP 默认使用 auto-ack，消费成功才确认
3. **重试 + DLX**：失败消息不会直接丢弃，经过 TTL+DLX 回环重试 3 次
4. **手动 ACK**：消费者设为 `MANUAL` 模式，明确确认消费成功

当前未实现但可进一步完善：
- **生产者确认（Publisher Confirm）**：确保消息到达 Broker
- **死信队列监控**：监控最终失败的消息并告警
- **幂等消费**：消费端检查文件状态，避免重复处理

### Q36：Ollama OCR 调用有哪些坑？你是怎么解决的？

**答：** 两个关键坑：

**坑 1：`think` 模式污染 OCR 结果**
- Ollama 默认开启 `think` 模式，模型会输出推理过程（"我看到一张图片，上面有..."），和 OCR 文字混在一起
- **解决**：调用时显式设置 `"think": false`

**坑 2：Jackson 序列化丢失嵌套字段**
- `Map<String, Object>` 中的 `options` 嵌套 Map，Jackson `ObjectMapper` 序列化时可能丢失这个嵌套结构
- 导致 `num_predict`、`num_ctx` 等参数不生效，模型使用默认值
- **解决**：用 `String.format` 手动拼接 JSON 请求体，不依赖 Jackson 序列化嵌套对象

调用参数：
- 模型：`qwen3.5:2b`
- `stream=false`, `think=false`, `num_predict=16384`, `num_ctx=8192`
- timeout=120s
- 实际性能：~3.1s/次，359 tokens，699 字符（因硬件和模型版本而异）

### Q39：搜索系统整体架构是怎样的？

```
前端 → core:8088 (SearchController) → RestTemplate HTTP → search:8081 (EsFileController)
```

### Q40：搜索的权重策略是怎么设计的？

**答：** 多层 Boosting 确保搜索结果符合直觉：

| 字段 | 权重 | 说明 |
|------|------|------|
| `fileName` (multi_match) | ×10 | 文件名匹配优先级最高 |
| `originText` (multi_match) | ×5 | OCR/文档文本匹配次之 |
| `originText.char` (multi_match) | ×2 | 字符级子字段兜底 |
| `fileName` (should boost) | ×50 | 额外 boost，确保标题命中结果排在最前面 |

搜索查询使用 `bool` 查询：
- `must`：multi_match 多字段匹配（至少命中一个）
- `should`：文件名额外加分
- `filter`：文件类型精确过滤（term query）
- `highlight`：文件名（整体高亮）+ 内容（3 片段 × 100 字符）
- `aggregations`：按文件类型分组统计数量

### Q41：ES 和 MySQL 的数据一致性怎么保证？

**答：** 多层兜底策略：

1. **实时同步**：文件处理到 `TEXT_EXTRACTED` 阶段 → `EsIndexServiceImpl.index()` → HTTP 写入 ES
2. **实时删除**：文件软删除/永久删除时同步调用 `EsIndexServiceImpl.delete(fileId)` 移除 ES 文档
3. **启动对账**：core 启动后轮询 search 服务，就绪后全量重建索引（清空 + 重新索引所有未删除文件）
4. **定时对账**：`@Scheduled(fixedDelay=30min)` 每 30 分钟全量重建，清理 ES 中的孤儿文档
5. **孤儿清理**：`@PostConstruct` 启动 30 秒后执行增量对账（ES 中有但 DB 中已删的 → 删除；DB 中有但 ES 中缺失的 → 补索引）

另外，`processStatus < 3` 的文件不写入 ES，避免半成品被搜索到。

**最终一致性**：秒级延迟，定时对账兜底。

### Q42：ES 挂了搜索功能怎么办？

**答：** 多层容错：

**search 端**（`EsFileServiceImpl`）：
- `search()` 捕获 `index_not_found_exception` → 返回空结果 `{list: [], totalCount: 0}`
- `deleteAll()` 捕获 `index_not_found_exception` → 返回 `deleted=0`

**core 端**（`SearchController` + `EsIndexServiceImpl`）：
- `SearchController.search()` 捕获 `RestClientException` → 返回 `"搜索服务暂不可用，请稍后重试"`（不抛 500）
- `EsIndexServiceImpl.index()` 捕获所有异常 → 记录 WARN 日志，"文件仍可正常使用"
- `EsIndexServiceImpl.delete()` 捕获所有异常 → 静默失败，不影响文件删除流程

整体策略：搜索是**增强功能**，不是核心路径。搜索挂了不影响文件上传、浏览、下载。

---

### Q43：IK 分词器的 `ik_max_word` 和 `ik_smart` 有什么区别？为什么选 `ik_max_word`？

**答：**

| 模式 | 策略 | 示例："中华人民共和国" |
|------|------|----------------------|
| `ik_max_word` | 最细粒度，穷尽所有词汇组合 | `中华人民共和国` `中华人民` `中华` `华人` `人民共和国` `人民` `共和国` `共和` `国` |
| `ik_smart` | 最粗粒度，非复合词 | `中华人民共和国` |

选择 `ik_max_word` 的原因：搜索场景**召回率优先**。用户搜索"华人"也能命中"中华人民共和国"为标题的文档。多个分词结果中只要有一个匹配就能召回，ES 会通过 TF-IDF/BM25 自动排序，细粒度分词不会影响精准度。

---

### Q44：为什么 `fileType` 聚合查询要用 `.keyword` 子字段？

**答：** `fileType` 在 ES mapping 中是 `keyword` 类型（不分词，精确匹配）。

在 ES Java Client 8.x 中，对 `keyword` 字段做 `terms` 聚合时，必须使用 `.keyword` 子字段（如 `fileType.keyword`）。如果不加 `.keyword` 后缀，ES 会尝试对 `text` 类型的 `fielddata` 做聚合，而 `fielddata` 默认禁用（因为内存开销大），导致查询失败。

这是 ES 8.x Java API Client 的一个常见坑，跟 ES 7.x 的 RestHighLevelClient 行为不同。

## 七、数据模型（Q45 ~ Q47）

### Q45：`files` 表的核心索引是怎么设计的？每个索引解决什么查询？

**答：**

```sql
PRIMARY KEY (id)
KEY idx_parent_delete (parent_id, delete_time)              -- 目录列表
KEY idx_md5_delete (md5, delete_time)                        -- 秒传检测
KEY idx_delete_time (delete_time)                             -- 垃圾站查询
UNIQUE KEY uk_parent_name_delete (parent_id, file_name, delete_time)  -- 同目录唯一文件名
```

| 索引 | 覆盖查询 |
|------|---------|
| `(parent_id, delete_time)` | `SELECT ... WHERE parent_id=? AND delete_time IS NULL` — 目录列表是最频繁的查询 |
| `(md5, delete_time)` | `SELECT ... WHERE md5=? AND delete_time IS NULL` — 秒传检测，O(log n) |
| `(delete_time)` | `SELECT ... WHERE delete_time IS NOT NULL` — 垃圾站列表 |
| `UNIQUE(parent_id, file_name, delete_time)` | 同目录不允许同名文件，**MySQL UNIQUE 视 NULL 为不同值**，所以已删除文件（delete_time != NULL）可以同名 |

注意：`uploader_id` 没有独立索引，查询需求目前通过其他索引配合实现。

### Q46：`files.origin_text` 字段有什么特殊处理？为什么？

**答：** `origin_text` 是 `LONGTEXT` 类型，MBG（MyBatis Generator）将其视为 BLOB 列。

这意味着：
- **不能用**普通 `selectByExample()` / `updateByPrimaryKey()` — 这些方法读不到 `origin_text` 字段
- **必须用**三个 BLOBs 版本的方法：
  - `selectByExampleWithBLOBs()`
  - `updateByExampleWithBLOBs()`
  - `updateByPrimaryKeyWithBLOBs()`
- Mapper XML 中定义了 `ResultMapWithBLOBs`（继承 `BaseResultMap`）和 `Blob_Column_List`

这是一个容易踩的坑：如果你用普通 `selectByExample()` 查文件，`originText` 字段永远是 null。

### Q47：分享链接的数据是怎么存的？为什么不用 MySQL？

**答：** 分享功能**完全基于 Redis 存储**，没有 MySQL 表。

```
Key:   allahpan:share:{code}
Value: {fileId, creatorId, expireTime} (Map)
TTL:   expireHours * 3600 + 3600 (最大 168h + 1h buffer)
```

选择 Redis-only 的原因：
- 分享链接有**天然 TTL**，过期后自动删除，Redis 的 TTL 机制完美匹配
- 分享数据是临时性的，不是需要持久化的核心数据
- 访问频率可能很高（多人同时访问分享链接），Redis 比 MySQL 快
- 分享码是 8 位随机 hex（`RandomUtil.randomString(8)`），碰撞概率极低

额外 1 小时 buffer 允许过期后短暂访问，避免时钟偏差导致的边界问题。

### Q49：如果用户量从 10 人增长到 10000 人，系统哪些地方会先出问题？怎么解决？

**答：**

**1. 文件存储 — 单 MinIO 实例**
- 问题：存储容量和 IOPS 瓶颈
- 方案：MinIO 集群 + 纠删码（EC:4），分布式扩展

**2. 数据库 — 单 MySQL 实例**
- 问题：`files` 表数据量增长（10000 用户 × 1000 文件 = 1000 万行），`parent_id + delete_time` 索引扫描变慢
- 方案：MySQL 主从分离（读写分离）；文件表按 user_id 分表；引入 TiDB 等分布式数据库

**3. 搜索 — 单 ES 节点**
- 问题：并发搜索 + 定时全量重建的 I/O 压力叠加
- 方案：ES 集群（3 master + N data），取消定时全量重建改为增量同步

**4. 缓存 — 布隆过滤器容量**
- 问题：10000 预期元素 / 1% FPP 的布隆过滤器在 100 万用户下误判率飙升
- 方案：扩大 bitmap 或改用分段布隆过滤器

**5. RabbitMQ**
- 问题：单节点 RabbitMQ 没有高可用
- 方案：RabbitMQ 集群 + 镜像队列

**6. 缩略图/OCR**
- 问题：10000 人同时上传，消费者处理不过来
- 方案：增加消费者并发数（`concurrency` 配置），Ollama OCR 考虑 GPU 服务器或云端 OCR API

### Q50：让你从头重新设计这个文件处理流水线，你会做哪些不同的决策？

**答：**

1. **用 MinIO Bucket Notification 替代轮询/消息触发**
   - 当前：文件上传到 MinIO 后，应用层主动发 MQ 消息
   - 改进：MinIO 原生支持 Bucket 事件通知（直接推送到 RabbitMQ/Redis/Kafka），省去应用层发消息的环节，减少耦合

2. **用 Kafka 替代 RabbitMQ**
   - 当前：RabbitMQ TTL+DLX 实现延迟重试，方案巧妙但配置复杂
   - 改进：Kafka 天然支持消息回溯、高吞吐、持久化更好，延迟消费可以用定时任务扫描
   - 反驳：但 RabbitMQ 对于命令式消息（做一件事）比 Kafka 更合适，Kafka 更适合事件流。家庭场景下 RabbitMQ 足够

3. **处理结果写成事件流而非状态机**
   - 当前：`processStatus` 枚举在主表上，状态转换是强耦合的
   - 改进：文件处理结果写成独立事件表（`file_events`），每个处理阶段写入一条 event。主表只关心最终状态，事件表记录完整处理历史，便于排查和审计

4. **缩略图生成改为按需（Lazy）而非上传即生成**
   - 当前：上传后立即生成缩略图
   - 改进：用户首次访问缩略图时才生成并缓存（CDN + MinIO）。因为许多文件上传后可能永远不被预览

5. **OCR 增加缓存层**
   - 当前：每次重试都重新调用 Ollama
   - 改进：对已成功 OCR 的图片 MD5 做缓存，相同图片不重复 OCR

6. **引入分布式锁处理并发**
   - 当前：单实例，没有并发问题
   - 改进：多实例部署时，同一个文件可能被多个消费者处理，需要 Redis 分布式锁（`SETNX`）保证幂等

### Q51：开发 DigestInputStream 流式 MD5 时，发现上传到 MinIO 后 MD5 永远是空的。怎么回事？

**答：** 这是一个**流只能消费一次**的经典问题。

**排查过程**：
- 现象：MinIO 上传成功，但 `digest.getMessageDigest().digest()` 返回全零
- 打断点发现 `DigestInputStream` 的 `read()` 确实被调用了，但 digest 值不对
- 检查代码：先调了 `minioUtil.putObject(inputStream, ...)`，上传完成后才调 `digest.digest()`
- 问题在于：MinIO SDK 的 `putObject` 在内部把整个流读完后，流已经到末尾了，但没有触发 `DigestInputStream` 的 `onClose` 之类的事件。实际上更根本的问题是——**在 `putObject` 返回后调用 `getMessageDigest().digest()` 的时机是对的，但问题出在之前某次重构时把 `DigestInputStream` 包在了 `BufferedInputStream` 外面**，导致 MinIO SDK 读的是内层 BufferedInputStream 而非外层的 DigestInputStream

**解决方案**：
```java
// 错误写法：DigestInputStream 没被读到
InputStream raw = file.getInputStream();
BufferedInputStream buffered = new BufferedInputStream(raw);
DigestInputStream digestStream = new DigestInputStream(buffered, MessageDigest.getInstance("MD5"));
minioUtil.putObject(key, buffered, size, contentType);  // ← MinIO 读的是 buffered，MD5 没更新
String md5 = Hex.encodeHexString(digestStream.getMessageDigest().digest()); // ← 空

// 正确写法：MinIO 读 DigestInputStream，让它同时流向 MinIO 和 MD5
InputStream raw = file.getInputStream();
DigestInputStream digestStream = new DigestInputStream(raw, MessageDigest.getInstance("MD5"));
minioUtil.putObject(key, digestStream, size, contentType); // ← MinIO 读 digestStream
String md5 = Hex.encodeHexString(digestStream.getMessageDigest().digest()); // ← 正确
```

**反思**：装饰器模式的嵌套顺序至关重要。`DigestInputStream` 必须是最外层被读取的流，才能截获所有 `read()` 调用。

### Q52：Ollama OCR 返回的结果总是带着一堆推理废话，怎么解决的？

**答：** 这是 Ollama qwen3.5 模型的 `think` 模式导致的。

**排查过程**：
- 调用 Ollama `/api/chat` 进行图片 OCR，预期返回纯文字，实际返回类似：
  ```
  好的，我来识别这张图片中的文字。图片显示...（推理过程）
  ---
  实际文字内容...
  ```
- 用 `curl` 直接调 Ollama 同样的问题，确认不是代码 bug
- 翻阅 Ollama 文档发现 qwen3.5 默认开启 `think`（思维链推理）
- 尝试在请求 JSON 中加 `"think": false`，但问题依旧——这就引出了第二个 bug

**深入发现**：用 `Map<String, Object>` 构造请求体，Jackson 序列化时 `options` 嵌套 Map 被扁平化处理，`think` 参数根本没到 Ollama 服务端。用 Wireshark 抓包对比 curl 和 Java 发出的 JSON，发现 Java 发的 JSON 少了 `options` 嵌套层级。

**解决方案**：
```java
// 放弃 Jackson 序列化，直接用字符串模板
String jsonBody = String.format(
    "{\"model\":\"%s\",\"messages\":[{\"role\":\"user\",\"images\":[\"%s\"],\"content\":\"%s\"}],"
    + "\"stream\":false,\"options\":{\"num_predict\":%d,\"num_ctx\":%d},\"think\":false}",
    model, base64Image, prompt, numPredict, numCtx
);
```

**反思**：框架的便利性在遇到复杂嵌套结构时可能变成障碍。HTTP 调用时，用 `curl` 先验证裸请求，再做 Java 实现。

### Q53：软删除后恢复文件时 MySQL UNIQUE 约束冲突怎么办？

**答：** 这是 MySQL `UNIQUE(parent_id, file_name, delete_time)` 索引与软删除模型交互产生的难题。

**场景复现**：

```
1. 用户在目录 A 下创建 "报告.pdf"（delete_time = NULL）✓
2. 用户删除 "报告.pdf"（delete_time = '2025-06-01'）← 进入垃圾站
3. 用户又在目录 A 上传了另一个 "报告.pdf"（delete_time = NULL）✓ ← 同名 OK，因为 UNIQUE 视 NULL 不同
4. 用户想从垃圾站恢复第 1 步的 "报告.pdf"
   → delete_time 设为 NULL
   → UNIQUE 冲突！目录 A 下已有 delete_time=NULL 的 "报告.pdf"
```

**解决方案**：
在 `restoreFile()` 方法中增加冲突检测：

```java
// 恢复前检查目标目录是否已有同名文件
FileExample example = new FileExample();
example.createCriteria()
    .andParentIdEqualTo(file.getParentId())
    .andFileNameEqualTo(file.getFileName())
    .andDeleteTimeIsNull();
List<File> conflicts = fileMapper.selectByExample(example);
if (!conflicts.isEmpty()) {
    // 自动重命名：追加速度时间戳
    String newName = addTimestampSuffix(file.getFileName());
    file.setFileName(newName);
    // 递归更新所有子孙的 filePath
    rebuildDescendantPaths(file.getId());
}
```

**反思**：设计软删除时容易忽略"恢复"和"同名"的边界情况。UNIQUE 约束的 NULL 行为在不同数据库中不一致（MySQL 允许多个 NULL，SQL Server 默认不行），设计约束时需要显式考虑。

### Q54：SSE 推送在开发环境正常，部署到 Nginx 后完全不工作。怎么回事？

**答：** Nginx 默认缓冲代理响应，会把 SSE 的流式推送"攒"起来一次发送，违背 SSE 实时性。

**排查过程**：
- 开发环境（Vite 直连 :8088）：SSE 消息实时到达 ✓
- 生产环境（Nginx → :8088）：客户端连接建立但不收到任何事件，断开时才一次性收到所有积压的消息
- `curl -N` 直连 :8088 的 SSE 端点 → 实时收到消息 ✓
- `curl -N` 经 Nginx 访问 → 卡住 ✓
- 定位到 Nginx

**解决方案**：在 Nginx 配置中添加 SSE 专用配置：

```nginx
location /api/file/watch {
    proxy_pass http://127.0.0.1:8088;
    proxy_http_version 1.1;
    proxy_set_header Connection '';
    proxy_buffering off;          # ← 关键：关闭缓冲
    proxy_cache off;              # ← 关键：关闭缓存
    chunked_transfer_encoding on;
    proxy_read_timeout 86400s;    # ← SSE 长连接不过期
    proxy_send_timeout 86400s;
}
```

**反思**：SSE 本质是"长连接 + 分块传输"，与常规 HTTP 响应模型不同。所有反向代理（Nginx、Apache、Cloudflare）默认都会缓冲，部署时必须显式关闭。踩过这个坑后我把 SSE 相关的 Nginx 配置写成了文档。

### Q55：大文件分片上传时，Spark-MD5 计算导致浏览器卡死。怎么优化？

**答：** 这是计算密集型任务阻塞主线程的典型案例。

**排查过程**：
- 上传 500MB 文件，分片 100 片，前端需要计算整个文件的 MD5（用于秒传检测）和每个分片的 MD5
- 文件选择后浏览器直接卡死 10+ 秒，Chrome 弹出"页面无响应"
- Chrome DevTools Performance 面板显示主线程被 `spark-md5` 的 `hash()` 调用持续占用
- 原因：`SparkMD5.ArrayBuffer.hash(buffer)` 在主线程中同步计算，大文件耗时线性增长

**解决方案**：Web Worker 分离计算：

```javascript
// useChunkUpload.js — 主线程
const worker = new Worker(new URL('../workers/md5.worker.js', import.meta.url));

// 发送文件切片给 Worker 逐片计算
for (let i = 0; i < chunks.length; i++) {
    worker.postMessage({ chunk: chunks[i], index: i, total: chunks.length });
}

// 接收 Worker 进度
worker.onmessage = (e) => {
    if (e.data.type === 'progress') {
        uploadProgress.value = e.data.percent;  // 实时进度
    } else if (e.data.type === 'complete') {
        fileMd5.value = e.data.md5;             // 最终 MD5
    }
};
```

```javascript
// md5.worker.js — Worker 线程
importScripts('spark-md5.min.js');

self.onmessage = (e) => {
    const spark = new SparkMD5.ArrayBuffer();
    // 逐片累加计算，发送进度
    spark.append(e.data.chunk);
    self.postMessage({ type: 'progress', percent: ... });
    // 最后一片完成时返回最终 MD5
    if (e.data.index === e.data.total - 1) {
        self.postMessage({ type: 'complete', md5: spark.end() });
    }
};
```

**反思**：任何时候处理大文件或密集计算，第一时间想到 Web Worker。用户不应为 MD5 计算支付 UI 卡顿的代价。另一个额外收获是 Worker 可以汇报计算进度，UI 体验更好。

### Q56：ES 索引重建期间搜索返回一半结果，怎么处理？

**答：** 这是全量重建和在线搜索之间的读写冲突问题。

**问题**：
- `rebuildAll()` 的实现是：先 `DELETE /_all` 清空索引，再逐条 `POST /index` 重新写入
- 在"清空"到"重建完成"的窗口期内，用户搜索返回 0 结果或不完整结果
- 文件数量多时（1000+），重建耗时可能达到几十秒

**解决方案**：引入**索引别名 + 原子切换**模式：

```java
// 改进后的重建流程
public void rebuildAll() {
    String newIndex = "allahpan_files_" + System.currentTimeMillis();
    
    // 1. 创建新索引（不是删除旧索引）
    createIndex(newIndex);
    
    // 2. 批量写入新索引
    List<File> files = getAllUndeletedFiles();
    bulkIndex(newIndex, files);
    
    // 3. 原子切换别名
    elasticsearchClient.indices().updateAliases(a -> a
        .actions(act -> act
            .add(addAction -> addAction
                .index(newIndex)
                .alias("allahpan_files_current")))
    );
    
    // 4. 删除旧索引
    deleteOldIndicesExcept(newIndex);
}

// 搜索始终指向别名
public SearchResult search(String keyword) {
    return search("allahpan_files_current", keyword); // 不是直接查真名
}
```

实际 trade-off：因为本项目数据量不大（家庭场景），最终没有采用别名方案，而是调整为**先建后删**——先在新索引构建完毕再删旧索引，把窗口期从不一致窗口缩短为"原子切换瞬间"。但面试中讲出这个思考过程是加分项。

### Q57：RabbitMQ 消费者在处理文件 A 时，文件 A 的另一个重试消息也到达了，导致并发处理同一文件。怎么避免？

**答：** 这是 TTL+DLX 重试和消费者并发之间的矛盾。

**场景**：
1. 消费者线程 1 正在处理 `fileId=100`（第一次）
2. 处理缓慢（Ollama OCR 耗时 10 秒）
3. 消费者线程 1 报错 → 发送重试消息，TTL 30s
4. 30s 后重试消息回到主队列
5. 消费者线程 1 其实还在处理第一次的 10 秒 OCR（网络慢）
6. 消费者线程 2 取到重试消息，也开始处理 `fileId=100`
7. 两个线程同时处理同一个文件！

**解决方案**：消费前加状态校验，消费时加 Redis 锁：

```java
@RabbitListener(queues = "allahpan.file.process", concurrency = "3")
public void handle(FileProcessMessage message) {
    // 1. 查当前最新状态，避免处理过期消息
    File file = fileMapper.selectByPrimaryKey(message.getFileId());
    if (file == null || file.getDeleteTime() != null) {
        return; // 文件已删除，丢弃消息
    }
    // 如果文件已被处理到更高阶段，跳过
    if (shouldSkip(file.getProcessStatus(), message.getCurrentStage())) {
        return;
    }
    
    // 2. Redis 分布式锁，防止并发
    String lockKey = "file:process:lock:" + message.getFileId();
    boolean locked = redisService.setIfAbsent(lockKey, "1", 60); // 60s 过期
    if (!locked) {
        // 有其他线程在处理，重新放回队列延迟处理
        fileProcessSender.sendRetry(message, 10 * 1000);
        return;
    }
    
    try {
        processByStage(message, file);
    } finally {
        redisService.del(lockKey);
    }
}
```

**反思**：异步系统的好处也是代价。消息驱动的系统必须时刻考虑幂等性——同一条消息被消费多次的结果应该是一致的。

### Q58：MinIO 对象名中包含中文导致下载时报 404。怎么解决？

**答：** MinIO 对象名（object key）中的中文字符编码不一致导致的问题。

**排查过程**：
- 用户创建文件夹 "家庭照片"，上传文件后 storageKey 中包含中文
- 上传正常，MinIO Console 能看到对象
- 下载时 404 Not Found
- 用 MinIO SDK 的 `statObject` 检查，对象确实存在
- URL 编码前后对比：SDK 内部对 key 做了 URL 编码，但中文编码不一致

**根因**：MinIO SDK 和 MinIO Server 对非 ASCII 字符的 URL 编码方式不同。SDK 3.x 版本在某些平台上使用了非标准的编码。

**解决方案**：**storageKey 整体避免中文**——文件路径只作为 `filePath` 存 DB 用于展示，MinIO key 使用纯 ASCII：

```java
// storageKey 生成——只用 ASCII 字符
String storageKey = String.format("%d/%s/%s%s",
    userId,
    YearMonth.now().format(DateTimeFormatter.ofPattern("yyyy/MM")),
    UUID.randomUUID().toString(),
    getExtension(originalFileName)  // 保留 .png .pdf 等
);
// 结果：1/2025/06/d27fed91-2fed-4e3e-bbcd-ce19dc3410c5.png
// 始终纯 ASCII，跨平台无编码问题
```

同时，`filePath` 字段保留完整的中文路径作为展示用：
```
filePath: "/家庭照片/2025春节/年夜饭.jpg"  ← 展示
storageKey: "1/2025/06/abc123.jpg"        ← MinIO 实际 key
```

**反思**：对象存储的最佳实践是 key 只用 URL-safe 字符（字母、数字、连字符、下划线、斜杠）。用 UUID 做 key 不仅避免了编码问题，还天然全局唯一。

### Q59：前端文件列表页在上传大量文件后性能急剧下降。怎么排查和优化的？

**答：** 这是典型的**列表渲染性能问题**。

**排查过程**：
- 用户反馈：文件数量超过 500 后，滚动列表明显卡顿，点击响应延迟
- Chrome DevTools Performance 录制：每次滚动触发大量重排（Layout Shift），耗时 200ms+
- Vue DevTools 检查：`FileBrowser.vue` 中每个文件项都是一个完整组件，包含图标、右键菜单、hover 效果等
- 关键发现：文件列表没有虚拟滚动，500+ 个 DOM 节点全部渲染

**解决方案**：三层优化组合拳：

**① Element Plus 虚拟化表格（首层）**
```vue
<el-table-v2 :data="fileList" :columns="columns" :width="1200" :height="600"
  fixed :row-height="48" :estimated-row-count="fileList.length" />
```
500+ 行只渲染可视区域内的 ~15 行，DOM 节点从 500+ 降到 ~20。

**② 缩略图懒加载（第二层）**
缩略图不是首屏必要内容，用 `IntersectionObserver` 延迟加载：
```javascript
const img = ref(null);
const isVisible = ref(false);
onMounted(() => {
    const observer = new IntersectionObserver(([entry]) => {
        if (entry.isIntersecting) {
            isVisible.value = true;
            observer.disconnect();
        }
    });
    observer.observe(img.value);
});
```
文件列表滚动时，只有进入视口的文件才开始加载缩略图。

**③ SSE 事件合并（第三层）**
批量上传时，SSE 可能短时间内推送几十个 `file-updated` 事件，每个事件都触发列表重渲染。加了一个 200ms 的防抖窗口，合并同一批次的事件再一次性刷新：
```javascript
let pendingUpdates = [];
let flushTimer = null;

sseEmitter.on('file-updated', (data) => {
    pendingUpdates.push(data);
    clearTimeout(flushTimer);
    flushTimer = setTimeout(() => {
        fileStore.batchUpdate(pendingUpdates);  // 一次更新，一次渲染
        pendingUpdates = [];
    }, 200);
});
```

**反思**：前端性能优化的铁三角：虚拟滚动（减少 DOM）、懒加载（延迟非关键资源）、批处理（减少渲染次数）。

### Q60：Docker Compose 启动顺序问题——ES 还没就绪，search 服务就连不上反复重启。怎么优雅处理？

**答：** 这是微服务启动依赖的经典问题。

**问题**：
- `docker-compose up -d` 后，ES 容器开始启动（需要 10-30 秒加载 IK 插件）
- `allahpan-search` 应用启动更快（5 秒），此时尝试连接 ES → `Connection refused`
- search 应用抛出异常 → Spring Boot 启动失败 → 退出
- 虽然有 `restart: unless-stopped`，但反复重启浪费资源，日志噪音大

**解决方案**：三层防御。

**① Docker 层：健康检查 + 依赖等待**
```yaml
# docker-compose.yml
elasticsearch:
  healthcheck:
    test: ["CMD-SHELL", "curl -s http://localhost:9200/_cluster/health | grep -q 'green\|yellow'"]
    interval: 10s
    timeout: 10s
    retries: 12
    start_period: 40s

allahpan-search:
  depends_on:
    elasticsearch:
      condition: service_healthy  # ← ES 健康后才启动 search
```

**② 应用层：Spring Boot 启动容错**
```java
// EsFileServiceImpl.java
@PostConstruct
public void ensureIndexExists() {
    int retries = 12;
    while (retries-- > 0) {
        try {
            elasticsearchClient.indices().exists(e -> e.index(INDEX_NAME));
            createIndexIfNeeded();
            return;
        } catch (Exception e) {
            log.warn("ES 尚未就绪，剩余重试 {} 次...", retries);
            Thread.sleep(5000);
        }
    }
    log.error("ES 启动超时，索引初始化失败，将依赖定时对账修复");
}
```
应用启动后不是立即失败，而是轮询等待 ES 就绪。

**③ core 模块等待 search 服务**
```java
// EsIndexServiceImpl.java
private void waitForSearchService() {
    int retries = 60;
    while (retries-- > 0) {
        try {
            restTemplate.getForEntity("http://localhost:8081/es-admin/files/search?keyword=__health__", Map.class);
            log.info("搜索服务已就绪");
            return; // 成功，退出等待
        } catch (Exception e) {
            log.info("等待搜索服务就绪... (剩余 {} 次)", retries);
            Thread.sleep(5000);
        }
    }
    log.warn("搜索服务启动超时 (5min)，稍后由定时对账补救");
}
```

**反思**：分布式系统中各组件启动速度不同，不能假设"先定义的先启动完"。优雅的启动依赖处理应该包含：健康检查 → 重试等待 → 降级运行（不阻塞主流程）→ 后台对账修复。
